# Эксплуатация и обновление

## Перед первым запуском исправленной версии

1. Перевыпустить BOT_TOKEN через BotFather: токен присутствует в старом errors.log.
   Удалить доступные посторонним копии старого лога. Новый токен не помещать в Git.
2. Остановить старые процессы бота и парсера, включая cron/nohup/screen/systemd.
   Файловые блокировки новой версии не защищают от уже работающего старого кода.
3. Сохранить PostgreSQL (`pg_dump -Fc`) и прежние ads.csv/errors.log вне репозитория.
   Ограничить права на копии: в них персональные данные, фильтры и старый токен.
4. Обновлять отдельный checkout/релиз. Старое виртуальное окружение оставить для отката.
5. Выполнить миграцию уникальности Telegram ID. Если найдены дубликаты, скрипт **прервётся**.
   Он намеренно не выбирает, чьи фильтры удалить. Сначала сравнить строки и сохранить правильные.

```sql
SELECT id_tg,count(*) FROM users GROUP BY id_tg HAVING count(*)>1;
```

```bash
psql -h 127.0.0.1 -U flatsdbuser -d flats_bot -v ON_ERROR_STOP=1 -f deploy/001_unique_users.sql
```

Миграция должна выполняться владельцем таблицы/администратором БД, если у пользователя
приложения недостаточно прав. Для новой БД после `schema.sql` выдать приложению права
SELECT/INSERT/UPDATE/DELETE на users и USAGE/SELECT на users_id_seq.
Проверьте имя роли: в старой документации использовались разные flatsdbuser/flats_admin.

## Установка на Ubuntu VPS

Команды предназначены для администратора сервера. Пути systemd-файлов рассчитаны
на `/opt/flats-bot`; используйте один и тот же каталог данных для обоих процессов.
Системный Python не заменять. Подойдёт установленный Python 3.11 или более новый;
зависимости и тесты проверены на 3.11, CI использует 3.11.

```bash
sudo useradd --system --home /var/lib/flats-bot --shell /usr/sbin/nologin flatsbot
# Разместить checkout исправленной версии в /opt/flats-bot.
cd /opt/flats-bot
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
sudo install -m 600 .env.example /etc/flats-bot.env
sudoedit /etc/flats-bot.env
sudo install -m 644 deploy/flats-bot.service /etc/systemd/system/
sudo install -m 644 deploy/flats-parser.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now flats-bot flats-parser
sudo systemctl status flats-bot flats-parser
```

Если роль flatsbot уже есть, повторять useradd не нужно. Checkout и .venv должны
быть читаемы этой ролью; записи нужны только в /var/lib/flats-bot и /var/log/flats-bot.
Systemd создаёт эти два каталога. При использовании Python, установленного в `/root`
или другом home-каталоге, `ProtectHome=true` заблокирует интерпретатор: установите
его в системный каталог или `/opt`, а не ослабляйте защиту вслепую.

`.env` сам по себе Python не читает: в production его читает EnvironmentFile systemd.
Для запуска из терминала экспортировать переменные, как в README. Не делать `source`
чужих конфигураций. Для CLI с production-настройками открыть администраторский shell,
экспортировать /etc/flats-bot.env и затем запускать команду под flatsbot с сохранением
этих переменных; не вставлять секреты в аргументы команд.

## Переменные

| Имя | Назначение |
|---|---|
| BOT_TOKEN | Новый токен основного бота |
| ADMIN_ID | Числовой Telegram user ID администратора |
| ALERT_BOT_TOKEN | Необязательно: отдельный бот для критических сигналов; иначе BOT_TOKEN |
| TELEGRAM_PROXY | HTTP(S) proxy для основного бота и рассылки; пусто = напрямую |
| PROXY | Старое имя, используется только если TELEGRAM_PROXY отсутствует |
| SOURCE_PROXY | Независимый HTTP(S) proxy для Onliner/Kufar; пусто = напрямую |
| ALERT_PROXY | Независимый маршрут критических сообщений; пусто = напрямую |
| database/user/password/host/port | Существующее подключение PostgreSQL |
| DATA_DIR | Постоянный локальный каталог SQLite и блокировок |
| LOG_DIR | Каталог журналов |
| MAX_PAGES | Максимальная глубина догрузки за цикл, по умолчанию 10 |

В новой версии нет обязательного прокси: оставьте пусто, если Telegram доступен
на VPS напрямую. Автоматического незаметного обхода настроенного прокси нет.
SOCKS не поддерживается общим транспортом парсера: задавайте HTTP(S) URL.
Встроенные HTTP_PROXY/HTTPS_PROXY намеренно не наследуются.
Перед рабочим запуском отправьте `/start` основному боту и, если настроен,
отдельному боту уведомлений. Бот не может первым написать человеку.

## Удобный просмотр журналов

Через SSH:

```bash
journalctl -u flats-bot -u flats-parser -f
journalctl -u flats-bot -u flats-parser --since '1 hour ago' --no-pager
journalctl -u flats-bot -u flats-parser --since today -g 'WARNING|ERROR|CRITICAL'
tail -f /var/log/flats-bot/parser.log
```

Отдельные `bot.log` и `parser.log`: UTF-8, время/уровень/модуль/поток,
5 MiB на файл и 5 архивов (около 60 MiB суммарно для двух сервисов).
INFO показывает начало/восстановление и размеры очередей; WARNING — временные
сбои; ERROR — ошибки обработки; CRITICAL — требует вмешательства.
Политика хранения journald отдельная: ограничивается настройками ОС.

Из Telegram, только от ADMIN_ID:

- `/status` — количество элементов очередей, статусы и возраст самых старых записей;
- `/get_errors` — текущие журналы обоих процессов; архивы остаются на сервере;
- `/get_stats` — последние 30 дней: Минск, одна комната, до $2000;
- `/get_users` — JSON с пользователями (не передавать посторонним);
- `/get_ads` — подсказка для полного экспорта на сервере;
- `/broadcast` — ручная административная рассылка; `/quit` отменяет ввод сообщения.

Ручная `/broadcast` имеет ограниченные повторы и отчёт об ошибках, но не является
постоянной кампанией: перезапуск процесса прервёт её. Надёжная дисковая очередь
относится к объявлениям. Статистика сейчас считает уникальные объявления,
попавшие в очередь получателей, а не весь рынок. Старый ads.csv не импортируется.

Обычные команды: `/start`, `/pause`, `/resume`, `/sources`. После перехода с Redis
пользовательские фильтры и isactive сохраняются в PostgreSQL, но незаконченные диалоги
Redis не импортируются. `/start` начинает настройку заново и временно приостанавливает
рассылку; `/resume` использует уже сохранённые основные фильтры.

## Какие события приходят администратору

- повторяющиеся сбои рабочих циклов;
- отсутствие успешного цикла 10 минут;
- зависший/погибший поток и перезапуск;
- неработающий polling Telegram более 5 минут;
- недоступность PostgreSQL интерфейсу после трёх проверок;
- очередь старше 30 минут;
- ошибочные объявления/неисправимая доставка, сохранённые для разбора;
- неверный токен Telegram, превышение MAX_PAGES, менее 100 MiB свободного места.

Одинаковый тип сигнала группируется (по шаблону сообщения) и отправляется не чаще
раза в 15 минут; разные ID одного вида ошибки смотреть в файлах.
Критические сообщения хранятся в alerts-bot.sqlite3/alerts-parser.sqlite3,
при ошибке отправки повторяются с задержкой до часа и переживают рестарт.
При заполненном диске сохранить новое сообщение может не получиться.
Если VPS выключен или потерял сеть, уведомление с самого VPS невозможно; для этого
нужен внешний контроль доступности у провайдера/на другой машине. Его здесь не настраивали.
Отдельный alert-бот и независимый ALERT_PROXY снижают общий риск, но не устраняют его.

## Очередь и восстановление

```bash
python -m src.service.manage status
python -m src.service.manage export > ads-inbox.jsonl
# После исправления конкретной причины:
python -m src.service.manage retry --table inbox --source kufar --id 12345
python -m src.service.manage retry --table outbox --source onliner --id 12345
```

Используйте тот же DATA_DIR и переменные, что у systemd, иначе откроется другая очередь.
Для Kufar комнат source в очереди — `kufar_rooms`, в пользовательском фильтре — `kufar`.
`retry` затрагивает только failed; выполненные рассылки повторно не ставит.
Экспорт JSONL содержит исходные объявления, не отправляйте его в публичный репозиторий.

Статусы inbox: baseline (исходная выдача), pending, done, failed.
Статусы outbox: pending, done, failed, blocked, cancelled.
Сетевые ошибки/5xx/401 повторяются; 429 учитывает retry_after; 403 отключает адресата;
400 для фото/альбома пробует текст со ссылкой, прочие постоянные ошибки сохраняются
как failed. После подписки/смены фильтров старые cancelled не отправляются снова.

Каждый час очищаются завершённые outbox старше 30 дней и исходные payload
обработанных/baseline inbox старше 30 дней; ключи дедупликации сохраняются.
Pending/failed не удаляются автоматически. Размер самого SQLite-файла после DELETE
может не уменьшиться, но освобождённые страницы используются повторно. VACUUM —
только при остановленных сервисах и достаточном свободном месте. Инбокс с ID
постепенно растёт: проверяйте диск и резервные копии.

## Резервное копирование и откат

Сохранять **PostgreSQL и весь DATA_DIR**. Простой согласованный способ — коротко
остановить оба процесса, выполнить pg_dump, скопировать DATA_DIR, затем запустить.
Не копировать только .sqlite3 активной базы без WAL: используйте SQLite backup API
либо остановку процессов. Копии держать вне этого VPS, регулярно проверять восстановление.

Для отката остановить новую версию, вернуть предыдущий checkout/venv, вернуть
нужные переменные и Redis для старого бота. Уникальный индекс users совместим со старым
кодом, удалять его не требуется. Старый парсер не понимает новую очередь: возможны
пропуски/повторы при откате. Не запускать старый и новый парсеры одновременно.

## Приёмка на VPS

1. Запуск без рассылки старой выдачи, три источника появляются в очереди как baseline.
2. Пройти настройку новым тестовым пользователем; проверить /pause, /resume, /sources.
3. Дождаться подходящего нового объявления, проверить фото/ссылку/цену/источник.
4. В отдельной тестовой установке прервать proxy/PostgreSQL: pending остаются,
   критический сигнал приходит, после восстановления доставка продолжается.
5. Перезапустить процессы: фильтры/FSM/очередь сохраняются, нет второй копии процессов.
6. Проверить резервную копию и свободное место.

Не имитируйте сбои на рабочей базе, пока не готовы прервать обслуживание.
В рабочий Telegram из среды аудита ничего не отправлялось; VPS не изменялся.
